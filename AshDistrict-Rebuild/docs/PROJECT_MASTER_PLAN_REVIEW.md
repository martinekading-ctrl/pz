# 《余烬街区》项目总规划（审阅稿）

> 2026-09-23。本文是供项目负责人核对目标的审阅稿，只整理现有决定、实际代码和待完成工作，不代表游戏内容已经验收，也不替代实际试玩。后续精细化修改以审阅意见为准。

## 0. 先说清楚：究竟要做什么

《余烬街区》是一款原创、横屏、单人离线的手机末日生存游戏。目标体验是：在明亮、绿色、有生活感的 2.5D 等距街区里自由移动；从道路进入外形各异的房屋；开门、翻窗、搜索现实比例的家具；在僵尸威胁下决定带走什么；处理饥渴、伤病和体力；最终回安全屋整理、休息并保存。玩家应当看懂空间，动作应当像真人，整段游玩应当自然顺畅。

参考《Project Zomboid》（下称 PZ）的是**可进入建筑、等距空间、屋顶/近墙遮挡处理、连续街区与生活化搜刮的体验标准**。目前的制作范围是手机简易版，不能用“玩法代码存在”代替“画面、比例、动作、操作已经达到目标”。参考图是街区构图与视觉密度的验收靶图，不是把整张房子贴图直接盖在地图上；可交互房屋必须是真正的门、墙、房间和物件。

### 本轮生效范围

- **平台**：先完成 Windows 调试版，再完成 Android 横屏真机版；正式交付以 Android 真机可玩为准。
- **世界**：现有连续小街区，现有 11 栋可进入建筑。玩家靠步行进入屋内、从屋内出来，不传送。地图可以以后扩充，但在首个街区达到质量标准前不继续铺新城区。
- **模式**：单人、离线、本地三存档槽。
- **核心内容**：一辆基础旅行车、一把基础手枪、少量近战武器、12–20 只左右的活跃僵尸、一处可认领安全屋、少量制作/维修、轻量天气。
- **明确不做**：多人、模组、动物、农业、完整 PZ 规模的物品与模拟系统。高楼、医院、完整超市、巨型城市、多车型、复杂枪械、复杂疾病/季节等属于旧版开放世界愿景；简易版上线前不据此扩量。未来若扩图，需要另立版本并重新评估，不是当前交付承诺。

## 1. 决策与资料的优先顺序

1. 用户在对话中最新确认的目标与反馈：房子不重复、真实比例、能进屋搜索、PZ 式遮挡、绿色明亮、手机看得清、动作不能跛或像高抬腿；这些高于旧文档中的“完成”字样。
2. `docs/simplified-mobile-scope-v1.md` 和 `docs/vertical-slice-roadmap-v1.md`：当前产品范围与顺序。
3. 本稿：把已定目标、代码现状、验收缺口放在同一处，审阅后才能成为新版总依据。
4. 各专项设计：建筑尺度、植被、背包、战斗、存档等；若与运行代码或用户反馈冲突，需要更新，不沿用过时描述。
5. `world-master-plan-v1/v2`、`road-network-plan-v3` 和 v4 大地图数据：历史规划与未来参考，不是当前 1.0 的任务表。

## 2. 玩家实际游玩的一局

1. 主菜单选择新游戏/三槽存档，选择职业和特质；新手可读懂移动、瞄准攻击、互动和背包。
2. 在安全屋或住宅附近出生。手机左摇杆移动，按住跑、点击蹲；镜头要兼顾角色辨识和周边危险。移动是连续自由行走，不按固定路线或格子跳。
3. 沿道路、人行道、庭院进到不同地块。能从建筑外形和入口判断去哪；树、草、围栏、车辆有真实尺度，不能遮住门。
4. 靠近门开关，必要时翻窗。进入建筑后屋顶隐藏或淡出，近侧墙降低，远侧墙和室内隔墙仍构成房间；人物、僵尸、门与家具正确前后遮挡。
5. 冰箱、橱柜、衣柜、床边柜等可搜物件在可达的正面操作区轻微轮廓发光；不显示菱形标识。搜索有时间和风险，打开页面可逐件“拿取/留下”，容量不够时余物留在容器。
6. 僵尸会游荡、听声调查、发现后追击、攻击门窗、进入室内；战斗需要有可信的走跑、转身、持械、挥击、受击、死亡动作。打开背包/搜索/治疗不暂停世界，不提供无敌。
7. 饥渴、体力、疲劳、伤口、感染、装备耐久和弹药让外出有代价。搜来的物资可使用、穿戴、维修、少量制作、放入车后备箱或带回安全屋。
8. 在安全屋治疗、睡眠、整理物品和保存。退出重进后，位置、房屋门窗、容器余物、车辆、尸体、伤病和世界时间等应能恢复。死亡可重新开始。

这是 1.0 的完整循环。若新玩家必须靠开发者解释才能找到入口、看懂操作或完成搜索，视为未达标。

## 3. 地图与镜头：先有完整布局，再铺模块

### 3.1 总体构图

- 当前可行走边界为 512×576 个逻辑格；1 格 = 0.5 米。先完成其中现有住宅、商店、道路、公园与庭院，不用整张大地图的面积制造“开放世界已完成”的错觉。
- **首个参考画面要逐项对照**：路口十字关系、左下蓝色住宅及围栏、左上砖住宅、右上便利店和停车场、右下车库及院地，连同绿地、道路宽度、树木疏密和镜头高度逐项比对。可为了玩家进入建筑、真实比例与遮挡机制调整几何，但任何明显增删或移位都要标出，不能用“风格差不多”代替参考图内容。
- 整体街区印象：灰色道路与清晰路口、大片自然绿色草地、数量克制的树和低草、不同体量的住宅与便利店/车库，整体白天明亮；没有大面积棕灰滤镜、杂物海、无故交叉的道路或毛坯空地。
- 路网按真实用途连接：主路、住宅支路、尽端回车位、店铺停车区、人行道和庭院入口。每条路都应有去处，车行和人行路径能解释建筑入口。道路、草地、地块的交界应无明显方形贴图接缝。
- 地块先确定占地、建筑方向、入口、窗户、围栏与庭院，再落树、灌木和草。绿化服从可行走与视线，不用密集草丛遮盖未完成地块。
- 地图按区块加载用于性能，但玩家游玩时不通过传送跨街区；后续扩图沿现有出口向外连续追加。

### 3.2 摄像机和可读性

- 基准画面 1280×720 横屏，正交 2:1 等距；当前默认镜头缩放代码为 0.68。这个数值是起点，不是最终观感保证。
- 同一场景用手机尺寸检查：人物能看清、房门能发现、附近威胁能提前察觉、HUD 不压住关键画面。室内与室外、步行与驾车可以按已定义规则切换镜头，但不能突然大幅跳变。
- 屏幕上的人物、车、树、床、门相互符合 1.75 米成人与 0.5 米逻辑格的尺度；比例要靠实机截图和走动录像验收，不能只看配置数字。

### 每栋建筑先画图后制作

1. **平面与尺度**：用米制坐标确定地块、建筑外轮廓、室内房间、主/副门、窗、门扇开启区、家具占地、交互正面、通行宽度和僵尸路径。现行基准：普通住宅约 6.5×5 米，层高约 2.7 米；普通门净宽约 0.9–1 米；成人约 1.75 米。
2. **外观结构**：地板、外墙、内墙、墙角、门洞、门扇、窗、屋顶、屋脊和门廊分模块组合。完整房屋图只作风格参考，不作整栋碰撞或一张不可进入贴图。
3. **家具规则**：床头靠实墙，衣柜/厨柜背靠墙，冰箱正面可达，桌椅有起身和绕行空间，门口与门扇回转区不摆柜。单人床约 1×2 米、双人床约 1.5×2 米、冰箱约 0.75×0.75×1.8 米、地柜标准段约 0.6×0.6 米；所有尺寸以统一建筑规范复核。
4. **PZ 式室内可视**：人在屋外能辨认屋顶和外墙；进屋后屋顶淡出/隐藏，近侧墙按墙段降低，远侧墙与房间隔墙保留；门框、踢脚线、墙角连续。人物和家具按脚点及实际墙位排序，不能穿墙、露出切片边角或被前墙整块挡住。
5. **验收**：入口可找、从入口可到每个房间、每件可搜物件只能从可达正面搜、开关门和翻窗不卡位、僵尸可通过应有的入口、屋顶/墙遮挡无跳动、存档后仍一致。

第一优先级是把 BlueHouse 做成有完整外观和室内的样板，再用同一素材库做完全不同的 ResidentialB01，证明复用不等于重复。现在 R02/R09 共用 H01、R03/R08 共用 H02 的底层模板，按设计目标必须分别拆成独立房屋；现有可进入不代表外观已交付。

## 5. 美术、素材与声音

- **视觉**：明亮自然绿草、柔和白昼光、略旧但仍像人生活过的城镇；现实比例、中等以下细节密度、缩到手机镜头还能分辨。不要厚重暗滤镜、塑料光、粗黑边或随意堆垃圾。每个室内房间控制 0–3 件小杂物。
- **统一素材库**：先选定一栋完整建筑的风格靶图，再做可复用墙/屋顶/门窗/地面/家具/植被/道路模块。可复用的是材质和物件，建筑轮廓、入口、窗户节奏、户型与内部身份必须不同。新素材优先查已有本地素材与来源，再补免费且允许商业使用的素材，最后才生成缺口；记录来源、许可、加工方式与文件位置。
- **植被**：树真实约 6–8 米，矮草 0.1–0.25 米、成簇野草 0.25–0.5 米、灌木 0.6–1.2 米；树干有碰撞，低草可穿行，树冠挡住人物时淡化。树根不得堵门、人行道或室内交互位置。
- **路面**：沥青、路缘、人行道、停车位与草地各有一致接缝；地面材质可重复平铺，不能忽然由道路变草地或出现方形裁切边。
- **音效**：脚步、开关门、搜索、武器、撞击、僵尸、天气和简洁环境底噪随场景状态播放；区分室内外音量。现有战斗音效只是基础，环境和交互音尚需补齐。
- **发布标准**：素材进入真实可玩地图后才算接入；来源必须可追溯，不能把未明确允许重新分发的第三方原始素材直接加入公开 GitHub。

## 6. 玩家、僵尸和车辆的技术与动作标准

### 当前真实架构

- 地图和玩法主体是 2D 等距逻辑；角色与僵尸的外观是有蒙皮的 3D 模型和 `Skeleton3D` 骨架，在透明 3D 视口中渲染后合成到地图。移动碰撞、门窗、战斗和搜索仍以 2D 世界逻辑计算。
- 车辆外观也是实时 3D，但当前由程序组合的车身/车轮网格构成，不是人物式蒙皮骨架；驾驶和碰撞仍由 2D 逻辑控制。
- 有 3D 骨架不等于动作自然。当前源 Walk/Jog 是原地循环；此前用步行片段重建跑步、后又给 Jog 烘焙脚部修正，用户实机仍看到跛脚/拐脚。**跑步状态为未通过验收，不能写成已修复。**测试场补的线性根位移也不是源素材自带根运动，尚未作为正式地图驱动。

### 人物动作必须如何验收

| 动作 | 可观察的合格标准 |
|---|---|
| 待机/起步/停步 | 重心连续，起停不突跳、不在静止时空踩 |
| 走路 | 左右步态均匀，脚掌接地，速度与步频匹配 |
| 跑步 | 成人自然小跑，左右对称；无高抬膝、跛脚、拖脚、腿穿模或明显脚底打滑 |
| 转向 | 移动中转向和原地 90°/180° 转身能衔接，不瞬间扭整个身体 |
| 持枪/近战 | 上下身配合，手持物与手骨对齐；攻击前摇、命中、收招与判定一致 |
| 僵尸 | 游荡与追击明显不同；追击有目的性，攻击是伸手抓扑而非拳击；受击和死亡可信 |

动作实现顺序：先对比同一骨架的完整、许可明确的动画片段（包括起停与转向），在独立测试场录**连续循环与多方向录像**；检查左右脚接触、滑步、转弯、停止和手机大小画面；再接正式地图，连同碰撞、持枪与僵尸追击一起实机复核。自动测试只负责轨迹/时序等数值，单帧截图不能替代整段动作验收。未达到上述标准就明确写“未通过”，不再说“改好了”。

|---|---|---|
| 输入与 HUD | 左摇杆移动、右摇杆按住瞄准松手攻击；跑、蹲、交互、装填；底部六格快捷栏；齿轮切换按钮布局，无独立换武和暂停按钮 | 基础已接入；检查安全区、误触、手指遮挡和真机分辨率 |

| 生存与医疗 | 时间、饥饿、口渴、体力、疲劳、头/躯干/手臂/腿伤、流血/感染、包扎、止痛、睡眠、死亡 | 规则已有；页面风险与提示需要试玩验证 |
| 制作与安全屋 | 少量绷带/修理/窗板制作；认领一处安全屋、睡眠与自动保存 | 只维持核心循环，不扩大制作树 |
| 供水供电 | 预设停水停电时间；水龙头、空瓶灌水、冰箱失电后鲜食变质 | 功能已有；要看玩家是否能理解变化 |
| 成长与开局 | 四项技能、四种职业、六个特质，影响动作或资源结果 | 功能已有；手机开局步骤应短而清楚 |
| 车辆 | 一辆旅行车，可上下车、驾驶、加油、撞击、后备箱与存档 | 玩法已有；当前程序车模不是正式美术，操控和碰撞需真机复核 |
| 天气 | 晴、阴、雨、雾只改变环境和显示，不叠加体温/疾病模拟 | 基础已有；室内外效果与性能待验收 |
| 存档/菜单 | 三槽、自动/手动保存、临时文件及备份、旧存档迁移、设置、教程 | Windows 测试版已有；Android 后台、崩溃和迁移必须实测 |

页面共通规则：背包、搜索、治疗、车辆检查等交互不会冻结世界，玩家可受僵尸攻击；同时需要清晰危险提示和迅速关闭入口，不能让 UI 本身成为难以察觉的陷阱。所有运行参数以当前代码与试玩结果为准，旧文档里的早期秒数/跑速不是不可修改的承诺。

## 8. 制作流程、版本与验收门槛

每个建筑或系统都按同一顺序：**需求与靶图 → 米制布局/交互草图 → 独立模块/数据 → 运行场景 → 连续试玩或录像 → 自动回归 → 手机视口检查 → 缺陷修正 → 审阅记录 → 提交 GitHub**。不以“素材生成了”“测试脚本通过了”或“截图好看”代替最后四步。

1. **先清理当前动作问题**：冻结不断改跑姿参数的做法；建立完整循环、多方向的基准录像，淘汰明显不合格跑步动作。通过用户目视验收后再将角色动作标记完成。
2. **0.34 建筑精修**：BlueHouse 样板、ResidentialB01 差异验证，再逐栋完成其余九栋。入口、室内墙、屋顶、家具比例、搜索面、通行、僵尸入屋、存档全部检查。
3. **0.35 手机 UI 与音频**：清掉调试层，背包/搜索/治疗/车辆页统一语言和尺寸，补声音及缺失反馈。
4. **0.36 Android 性能与真机**：中低端机帧时间、视口/GPU、内存、发热、电量、横屏安全区、后台恢复、签名 APK/AAB。
5. **0.37 外部试玩**：陌生玩家无需口头引导完成 20–30 分钟核心循环；修阻断、穿模、存档、死亡重开、读档与长时间稳定性问题。
6. **1.0 候选**：只做发布修复和商店验收，不临时加新城区或复杂系统。

完成的定义分四层记录：**设计已确定 / 代码已接入 / 自动检查通过 / 实机与目标观感验收通过**。只有第四层才叫完成。每个缺陷记录复现步骤、设备或分辨率、实际录像/截图、期望效果与修复验证；多次调整无效时停下重选素材或方案。

## 9. 目前已经偏离目标的地方（不能回避）

1. **角色跑姿**：反复修改仍出现高抬脚、跛脚/拐脚。过去依据脚踝高度和单帧截图说“改好”是不成立的；动作质量当前未验收。工作区还有未提交的动作试验文件，GitHub 现有代码也不等于合格跑姿。
2. **建筑多样性**：规划要求 11 栋各有身份，现有八栋目录住宅里有两对复用完整户型，且部分特殊屋顶/门廊/车库外观未实现。现在只能称“可进入的初版”，不能称每栋都已完成。
3. **室内比例与遮挡**：已有米制布局和碰撞检查，但用户实际看到过家具贴墙穿模、墙体难看、门不明显。单纯可达性测试不能证明视觉正确；需逐屋镜头验收。
4. **美术混合**：旧式 2D 家具/植被、程序化车与 3D 角色并存，透视、光线和细节密度还未统一。部分素材文档仍按纯 2D 人物/车编写，不能直接当现行接入规范。
5. **完成度数字过早**：旧文件写“上线约 70%、系统约 94%”，但没有 Android 真机、陌生玩家试玩与合格动作录像支撑。继续使用这些数字会误导；应改成逐项验收状态。
6. **文档互相冲突**：旧动作文档有 3.2 米/秒跑速，旧操作文档有 3.8 米/秒，当前工作区是 2.7 米/秒；旧总素材规范说 2D 人物序列帧，当前运行时是 3D 骨架；旧开放世界方案与当前 11 栋冻结范围不同。后续以本稿审阅后的统一规范和代码实测为准。
7. **发布状态**：Windows 调试/测试路径存在，Android 签名包、中低端手机性能与长期稳定性尚未完成，不能称可上架。

## 10. 审阅时最需要核对的目标

- 首个版本是否确认为 **“11 栋各不相同、能进入搜索的连续街区”**，而不是旧规划中的医院、高楼与完整城镇。
- 参考图是否作为 **整体构图、比例、明亮绿色风格** 的目标，同时保留真正的可进入室内，而非一张整屋贴图。
- 是否同意把 **连续动作录像和真实手机试玩** 作为动作/UI 的完成门槛；此前任何“单帧截图通过=完成”的记录均不再计入。
- BlueHouse 样板、其他房屋差异化、动作、UI/音频、Android 验收这一制作顺序是否符合优先级。

本稿只用于核对方向。未经实机验证的条目保持“待验收”，不把目标写成已经交付。
